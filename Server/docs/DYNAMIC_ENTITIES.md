# Recovered scene-object identity

The five pinned multiplayer maps contain 87 initially active, non-trigger colliders with a `dynamicOwner`: 40 cover shields and 47 other scene colliders. Twenty-nine of the latter have barrel names (Aztec 3, City 2, Desert 6, Park 10, Snow 8). The remaining City/Snow objects include beams, containers and train parts; their destructibility must be verified from their scene components before treating them as damageable.

The exported hierarchy path is **not** an instance ID. All three Aztec barrels and all six Desert barrels share a path within their respective map exports. `RecoveredBattleMap` therefore retains the exact zero-based `colliders` array index for every active dynamic shape. The index is stable within the pinned map content and, together with the map revision/hash in the signed match manifest, identifies one serialized collider. `MapHit.ColliderIndex` returns it, `DynamicColliders` exposes the catalog, and the raycast can suppress one index without suppressing every object at the same path. The existing shield owner-path filter remains compatible.

`Tools/Extract-BarrelSceneBindings.py` reads the original five Unity scene YAML files, checks each file against its pinned SHA-256, locates GameObjects with both `Barrel` and `DestroyableObject` components, computes their world transforms, and pairs each barrel collider with one exported collider row. It compares the GameObject name as well as position because two Park barrels occupy the same position. The resulting [29 file-ID/component bindings](../content/recovered-barrel-scene-bindings.json) include each serialized shot coefficient, all exactly 1. They are pinned by `BarrelBindingsRevision` in the combat manifest and validated by `BarrelSceneCatalog` at Worker startup. This makes the original scene GameObject, collider, Barrel and DestroyableObject file IDs available for later Client view association. Re-run the extractor after intentional scene-content changes; a changed scene digest or ambiguous match aborts extraction.

This is identity for **collision**, not yet a complete gameplay entity ID. `BarrelSourcePolicy` validates the 43 recovered `Google2u.Levels` rows and reproduces `Barrel.Awake`'s `50f + ((float)playerLevel / maxDisplayLevel) * 6f` health formula; `BarrelLifecycle` applies confirmed source shot damage and a one-time death transition. Recovered `PhotonView.isMine` treats an inactive/zero owner as owned by `PhotonNetwork.isMasterClient`; all scene barrel views inspected have `ownerId: 0`. The allocator can therefore sign both zero-based `PlayerLevel` values and `SceneMasterPlayerId`. A live match with these fields initializes its host-owned `BarrelMatchSimulation` from the selected master's level; neither field is accepted from a player packet. `BarrelMatchSimulation.CommitPlannedChain` now rederives a preview against current host state, rejects altered/stale plans before mutation, and commits all barrel health/revision/collider changes together. A separate authenticated `MatchBarrelPoll`/`MatchBarrelBatch` now exposes the source count, shared maximum HP and changed barrel rows with their recovered scene GameObject file IDs for reconnect; unchanged revision-zero barrels are implicit. Keeping this outside `MatchSnapshot` is required by the 1,200-byte UDP limit when both full rifle poses are present. The portable `BarrelStateTracker` binds this read to the pinned collider-to-GameObject map, fills untouched rows at source HP, and rejects identity mismatches or revision rollback. `MatchEngine` now applies confirmed source projectile hits to barrels, commits depth-first neighboring barrel chains, projects current-pose player blast damage, and emits damage/death events. A Park source rifle encounter and a real two-peer UDP run prove live health, death, reconnect state and identical ordered events. `SelfHostedBattleClient.BindBarrelCatalog` and `BarrelStateReceived` now deliver the verified projection on Unity's main thread, with a full poll before cursor acknowledgement if an event revision is missing. The normal battle controller still has to bind the recovered scene objects and consume those callbacks.

The `Barrel` source triggers `Explosion` on death with `explodeDamage=180` and `damageAmount=15`. `Explosion.Explode` uses a 1.1-unit dead radius and 1.8-unit hurt radius and overlaps `destroyableObjectsMask`. `BarrelExplosion.Resolve` reproduces the selected-target scalar branch: 180 damage inside the dead radius and squared falloff toward 15 outside it. Its caller must first reproduce Unity's `Physics.OverlapSphere`: a collider whose bounds overlap can receive the minimum 15 even when its transform center is beyond 1.8 units. `RecoveredBattleMap.DynamicSphereCandidates` retains exact collider index, transform position and source bounds. A [Unity 2018 reference audit](../content/unity-barrel-overlap-reference.json), generated by `Server/tools/UnityBarrelOverlapAudit.cs` in a disposable project, compares all 29 source barrel centers at both 1.1 and 1.8 units. The server's AABB candidates exactly match Unity's 103 selected destroyable hits in those 58 probes, including one City beam hit. The audit's raw collider order is repeatable across two fresh Editor runs but differs from exported collider-index order in 20 probes. `BarrelOverlapOrderCatalog` pins and validates the 1.8-unit order in the combat package; `BarrelChainPlanner` previews synchronous, depth-first neighboring barrel deaths. In Park, one Shiver leaves a barrel at 1.467 HP, a nested explosion occurs, and another Shiver kills it. The planner preserves barrel and City beam hits in one `OrderedEffects` stream, with separate projections for each target family, and does not publish partial state. The beam's serialized `DestroyableObject` maximum is `1E+10` as a 32-bit float; subtracting either source blast amount leaves its HP unchanged at that precision. The planner rejects any newly selected nonbarrel target until its lifecycle is modeled. This is evidence for those fixed scene/barrel-center queries, not arbitrary sphere placement or moving players.

`DestroyableObject.Awake` changes the GameObject layer to `destroyableEntitiesLayerNumber` (8), while the exported barrel colliders still carry their serialized layer 0. A scene-master-bound match now uses layer 8 in its host raycast and sphere candidate filters. Resolved projectile collisions carry the exact collider index, and a source-level barrel state can suppress only its own collider. The replacement host has source-center barrel/beam targets and current-pose player blast projection; stable entity generations and normal Client view binding remain open. The City beam retains its source `1E+10` float HP under each barrel blast. No reward or objective credit is granted from a collider index alone.

For player targets, the recovered rig has one box and one sphere hit part. A second [Unity 2018 overlap audit](../content/unity-player-explosion-overlap-reference.json), generated by `Server/tools/UnityPlayerExplosionOverlapAudit.cs` in the disposable project, samples idle, firing and running at three times each. All 180 radius/edge probes match `PlayerHitbox.OverlapsSphere` exactly; when both parts overlap, Unity returns body before head in this audit. The host rig now also retains each part's transform origin, verified against matching Unity samples, because `Explosion.Explode` measures damage falloff from the part transform rather than the collider center. `ExplosionSourceCatalog` pins `PlayerExplosiveCoef=0.88` and `PlayerExplosiveOvertimeCoef=0.6`, and `BarrelExplosion.ResolvePlayer` applies the first selected part's weight and appropriate multiplier through the existing damage-order kernel. The `ShieldExplosionCoef=2` row belongs to `MissileExplode`, not `Barrel.OnDeath`'s ordinary `Explode` call. `BarrelPlayerChainResolver` now projects the current moving-player pose against every barrel death in the ordered chain, carries HP through repeated blasts, and leaves match state untouched until all effects can be committed. It uses stable roster order as the replacement host tie break for moving player colliders; Unity broadphase ordering beyond the sampled poses is not proven. Live match commit and terminal handling are wired, with source-ID barrel and player explosion events; normal Client view consumption and damage for future soldier/vehicle targets remain open. A host geometry check places the recovered idle rig at all 40 cover points and finds no stationary cover pose inside any source barrel blast. A separate reachability regression samples 31 positions per recovered cover-route segment with one run-frame collider and likewise finds no barrel overlap. This sampled check is not a continuous-path or all-animation proof; later movement modes and spawned entities still need battle-path verification.

Live barrel impact now passes the match's overtime state into that resolver. The pinned MainScene values select 0.88 normal and 0.60 overtime player-explosion coefficients; a source-bound chain test keeps the hit order fixed and verifies that the overtime projection leaves more player HP. A positive live blast still awaits a reachable moving-player or spawned-entity path.
