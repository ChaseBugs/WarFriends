# 1.4.0 deathmatch army deployment evidence

`../content/recovered-army-deployment.json` binds the 24 `SpawningManagerDeathMatch.armyDefinitions` in `MainScene.unity` to their `LevelBehaviour` and `UpgradeSlots` component file IDs. The extractor resolves each upgrade-slot C# type to its exact `Google2u.ArmyUpgrades.NAME` row in `recovered-battle-content.json`. Run `python Server/tools/extract_army_deployment.py --check` at the repository root to detect source or generated-artifact drift.

The scene's serialized `unitsCounts` are preview values, not live options. `SpawningManagerDeathMatch.InstanceOnPlayerDataLoaded` replaces them with the row's `SPAWNS` sequence and assigns contiguous global option indexes. That yields **48 options**. For example, Assault is serialized as 3/5 but runtime `SPAWNS` is 2/4. Each option's power is `count * TOTALPOWER`, and its extra cooldown is `count * COOLDOWN`. The runtime base cooldown is `Constants.SendUnitsCoolDown = 1`, overriding the scene's serialized 3. Maximum starting energy is `Constants.MaxEnergy = 8`.

Several different scene behaviors resolve to the same recovered upgrade-slot C# type and therefore the same sheet row; the loader preserves those source bindings instead of inferring rows from unit display names. The combat package pins the generated artifact hash and verifies its option counts, power, and cooldown against the separately pinned ArmyUpgrades sheet at startup.

`../content/recovered-army-spawn-points.json` pins 101 spawn components across the five multiplayer scenes: the normal, drone, assault-helicopter, car, and helicopter collections referenced by each scene's `MapDefinition`. Each row retains the ordered collection slot, Unity file IDs, concrete component type, faction, world position, full local transform chain, and car/air-route reservation identity. Run `python Server/tools/extract_army_spawn_points.py --check` to detect extraction drift. `WarArmySpawnPointAudit.Run` loaded all five scenes in Unity 2018.3 and matched all 101 types, factions, and positions; the Editor's scene-object local-ID API returned zero, so file-ID binding is proven by the scene YAML references and pinned scene digest rather than that API. `BattleCombatContent` validates the artifact hash, all source map revisions, identities, order, finite transforms, and recomputed world positions before match allocation.

The army artifact now also records each concrete `LevelBehaviour` class and serialized soldier spawn-point mask. `ArmySpawnPointSelector` routes soldiers and Mech to the normal collection, Drone to drone points, assault helicopter and transport helicopter to their own collections, and cars/tank to car points. It applies faction/type filtering and source Commando/Warper/Shotgunner/Swat/Flamethrower farthest-opponent selection; vehicles require an explicit host availability check. Minigunner uses the recovered `List<SpawnPoint>.Sort` comparator with alternating parity. Run `pwsh -NoProfile -File Server/scripts/AuditMinigunnerSort.ps1` at the repository root to repeat the Unity 2018.3 probe: two- and three-item lists select the last source point on even calls and the first on odd calls; all five pinned maps have only two or three eligible normal points per faction. The host keeps parity per match to prevent concurrent matches changing one another's spawns. A live Park match test proves the first Minigunner entity uses the expected source component. The selector is wired to live spawn records, although AI movement and attacks remain open.

The allocator may now provide both players' `EquippedArmyUnitIds` and the equipped subset `NewArmyUnitIds` in a live match manifest. `MatchManifest.Validate` detaches and checks the arrays; combat-package validation binds every equipped ID to the pinned scene before `MatchEngine` creates either player's deployment state. `ArmyDeploymentState` groups eligible options by recovered `UnitType`, samples one option per type, drops one if all four types are present, and then selects a three-option hand. Its first hand promotes the last eligible option of a new unit, replacing the same behavior, then the same type, then slot zero as the Client does. It reserves capacity, enforces energy and cooldown, schedules individual spawns nine 30-Hz ticks apart, and refunds a confirmed entity death once. If no eligible unit remains, the hand is empty; the source Client's unowned Assault fallback cannot become host authority. Deathmatch uses the Client's Classic spawning policy. Fixed-spawning preference belongs to War Arena and remains for that mode's implementation.

The authenticated `MatchArmyPoll`/`MatchArmyBatch` UDP channel exposes only the caller's issued hand and current energy/cooldown counters. Its read is stable across retries until a deployment consumes the hand. `DeployArmyCommand` now consumes an offered option through the sequenced, replay-safe match command path; the host rechecks energy, cooldown, unit capacity, free source routes, and event capacity. It schedules 0.3-second units and publishes `ArmySpawned` events with the owner, option, unit ID, scene spawn-component ID, route reservation ID, and position. A real two-peer Park test confirms an unoffered option is rejected and both peers replay the same source-bound records. The portable Unity SDK provides `PollArmyAsync` and `DeployArmyAsync`; `SelfHostedBattleClient` exposes these through `ArmyOffersReceived`, `RefreshArmy`, and `DeployArmy`.

`MatchArmyEntityPoll`/`MatchArmyEntityBatch` expose the complete active entity set in four-row UDP pages. A separate army revision prevents pages from different states being combined; the portable SDK retries changed scans and validates owner, identity, unit, source point, and finite position. A real two-peer test forces a five-entity, two-page result and verifies a new signed session reconstructs it without event history. `SelfHostedBattleClient.RefreshArmyEntities` presents that projection on Unity's main thread.

The recovered `SpawningManagerDeathMatch.AiObjectOnAiObjectKilled` credits a suicide's power to its owner but an ordinary death's power to the opposing faction, then removes the unit from the family spawn count. `MatchEngine.ConfirmArmyDeath` now reproduces that rule as a **host-only** transition. It verifies the live entity and route reservation, removes the entity once, releases the route, updates the reconnect revision, and emits an `ArmyDied` event with the energy recipient. A repeated death has no effect. There is deliberately no client kill packet. `BattlePlayerState.confirmed_army_spawns` increments only after the host inserts each scheduled entity, and `confirmed_army_losses` increments only after its one-time host death/removal. The counters freeze in terminal evidence; a deployment acceptance and a replayed command do not manufacture a spawn. Recovered `StatsManager.MatchStats.DeployUnit` instead increments `unitsDeployedSpecific` once and `unitsSpawnedSpecific` by the selected option count at selection time, with `deployClicks` only for a click. These host counters are intentionally separate from those optimistic Client statistics; per-unit/type result fields and click provenance remain open.

The event poll now measures each candidate page against the complete authenticated 1,200-byte packet envelope. It stops before the first event that would exceed the MTU and leaves that event at the next cursor, so wider lifecycle records cannot make a valid match UDP read fail or skip history.

These are **host entity records, not combat-capable AI yet**. There is no movement/targeting/damage simulation to call the death transition, and no connection to the scene's original spawning/visual controller. Backend must also authoritatively provision ownership/upgrades. Until those pieces are implemented, deployment cannot close B13 or contribute to result/reward authority.

The recovered Client now has an explicit opt-in army-card bridge: after `SelfHostedBattleClient.Connect(grant)` and after `SpawningManagerDeathMatch.InstanceOnPlayerDataLoaded` has rebuilt the runtime option indexes, the scene owner can call `await client.BindArmyManager(Singleton<SpawningManagerDeathMatch>.instance)`. The host's `MatchArmyBatch` maps its three exact option indexes to the original `ArmyUnitDefinition` objects and raises the existing `ArmyChanged` event. The original card click passes through `SendUnit`, which sends a sequenced `DeployArmy` command and records a successful clicked deployment only after the host returns `army-deploying`. Once bound, the manager remains in self-hosted mode for its lifetime: disconnect/unbind clears the cards and subscriber, and cannot fall back to Photon hand, spawn or energy RPC handlers. A new session needs a new scene manager. Unbound local campaign/tutorial behavior retains its original path. `SelfHostedArmyBridgeAudit.Run` verifies the mapping, stable re-poll, invalid-option rejection, empty-hand projection and fail-closed teardown in Unity 2018.3. This is not connected by a normal battle-scene bootstrap yet, and the server's entity rows do not instantiate the original unit visuals; those are the next Client integration gates.

The first B14 combat-stat input is now pinned: `ArmyDeploymentCatalog.BaseStats(unitId, normalUpgradeIndex)` reads the exact `HP` and `DAMAGE` row from each family’s source-bound `Google2u.DBUpgradeSlots*` sheet in the hashed combat package. Some sheets contain zeroed spacer rows between upgrade lanes; these remain visible in the source but the lookup rejects their zero HP as unplayable. `BehaviourDefinititon.ScaleDamageAndHP` and `AIObject.SyncUpgradesRPC` show that normal-row values still need the recovered upgrade scale, perk, and special/elite setup before becoming a live health or hit-damage value. Backend provisioning does not yet supply those authoritative modifiers, so this lookup is deliberately not used to resolve hits or kill entities.

The trusted match manifest can now carry `ArmyNormalUpgradeIndexes` in the same order as `EquippedArmyUnitIds`. Validation detaches both arrays, rejects mismatched length or non-index values, and binds every supplied stage to a playable HP row in the pinned combat package before match creation. Current provisioning does not yet populate this field from the Backend, and no stat is accepted over UDP. The remaining B14 authority path is Backend ownership/upgrade projection, source perk and scaling rules, then deterministic host AI targeting, movement, attacks, and damage.

`ArmyUpgrades.STARTINGSPECIAL` now bounds the normal lane; a later positive special/elite row cannot masquerade as a normal upgrade. `ComposeStats` reproduces `UpgradeSlotsGeneric.LoadData`'s additive normal + optional special + optional elite HP/damage pass, with each optional index confined to its recovered lane. The trusted manifest can project both optional stage arrays, using `-1` for a lane that is not bought; both participants' arrays must be present together, align with their equipped unit order, and detach before hashing/retention. This composition is the pre-perk, pre-mode input to the vitality calculation.

The allocator can now project separate `PerkCoefficient` and `UpgradeScale` health factors per equipped unit. If both participants have complete trusted factors, the host initializes a private health ledger for each spawn from the composed source rows, applies the perk factor then the upgrade scale, and accepts nonfatal/fatal damage only through its internal `ApplyArmyHostDamage` transition. Fatal damage uses the existing host-confirmed death path, releasing the reservation and crediting the opposing faction once. There is no client damage packet or hit claim. Current Backend provisioning does not yet calculate these factors, and no projectile/AI collision path calls the damage transition, so this does not make deployed units combat-ready yet.

`AIObject.SyncUpgradesRPC` applies `UnitUpgrades.scaleDamage` after loading the normal, special and Elite rows; `BehaviourDefinititon.ScaleByPerk` changes HP, speed and shot speed, but not damage. The trusted manifest now accepts a separate `ArmyDamageScales` array aligned to each equipped unit for both players. The combat package validates its finite bounds and source-stage product before allocation. Each spawned unit retains that effective damage in a private host ledger, removed on confirmed death. A changed allocator array cannot alter the retained manifest, and no UDP packet can supply a damage factor. The ledger is an input for future source-backed attack decisions, not evidence that infantry already attacks.

Movement speed uses a different source path: `UpgradeSlotsGeneric.LoadData` overwrites serialized behavior `baseSpeed` with the family's `ArmyUpgrades.MOVEMENTSPEED`, then applies `Perk.speedCoef`. The deployment artifact pins both values for all 24 families and validates runtime speed against the recovered sheet. The signed allocator manifest may include aligned `ArmySpeedCoefficients`; allocation validates the effective source-sheet product, and a spawned entity keeps it in a private speed ledger until death. This does not yet advance the entity through Unity-equivalent navigation.

The paged `BattleArmyEntityState` protobuf now includes `max_health` and `health` when trusted vitality exists, or both zero when it has not been provisioned. A nonfatal host hit advances the entity revision and updates the row, forcing an in-progress reconnect scan to restart; the portable SDK rejects non-finite, negative, dead-but-active, or over-maximum health. The four-row worst-case page still fits the authenticated 1,200-byte UDP envelope. These are health projections, not client-owned damage evidence.

`SelfHostedBattleClient` now refreshes the paged army entity set every 0.5 seconds while `ArmyEntitiesReceived` has a subscriber, in addition to the initial reconnect scan and explicit refresh API. That gives a Unity scene consumer current spawn/despawn and health projections. The normal battle scene still does not bind this callback to original unit visuals or disable Photon ownership of those objects.

`../content/recovered-army-rusher-points.json` now pins the four `PlayerPoint.rusherPoints` component file IDs, serialized indexes and world positions at each of the eight defend positions in all five multiplayer scenes: 160 distinct slots total. Run `python Server/tools/extract_army_rusher_points.py --check` after scene changes. `SoldierBehaviourRusher.CanBeSpawned` requires at least `numberOfEnemies` free slots at the opponent's current defend position, and the host applies that gate to offers and deployment, counting queued Rushers before their spawn ticks. On spawn it follows `GetInitPoint`'s nearest free slot comparison, including its preference for indexes 0/1; once four points are occupied across the opposing side, it leaves the entity on the ordinary spare route instead. Confirmed death releases the exact reserved slot. A real match test verifies queued Rushers close offers, all four slots fill across Rusher families, and offers reopen after death. Rusher movement, target switching and presentation remain open.

Issued hands can become stale while an earlier vehicle batch is pending. `MatchArmyPoll` rechecks cached options against current capacity, source routes and Rusher slots, then withdraws and recomputes a stale hand before presenting it. Pending vehicle spawns now count against the remaining routes in their source collection, so a queued tank cannot leave the last car route apparently free for a buggy. A deployment command also discards its hand if a route or slot disappears between poll and command; replay of that rejected command retains its original rejection. A live Park match test queues a tank after the first car, verifies the buggy is not offered before the tank's spawn tick, and verifies the same unavailable state after spawn. Cooldown and energy rejections keep the hand because those conditions may resolve without a route change.
