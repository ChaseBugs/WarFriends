# Live rifle combat and cover movement

The opt-in `unscored-rifle-combat` match mode connects the real UDP Worker to server-owned animation, cover movement, muzzle placement, bullet flight, collision and player damage. It is a bounded integration checkpoint, not a complete multiplayer game.

Configure `Battle__CombatContentManifestPath` as described in [COMBAT_CONTENT.md](COMBAT_CONTENT.md), and supply a signed, operator-owned match manifest through `Battle__MatchManifestPath`. Set its mode to `unscored-rifle-combat`, its catalog revision to the package revision, and both players' `WeaponUpgrade` and exact `Stats.CreateManifest` values. Each player also requires a validated combat-health definition, a legal starting cover and `MovementSpeed=1`, matching `GameControllerOnline.InitPlayer()`. War Arena speed rules are outside this unscored mode. Health remains trusted allocation input; Backend ownership/profile allocation is unfinished.

This mode selects map geometry from the pinned package itself. It uses exported cover rotations, recovered GlobalStorage faction bullet masks, blended player parts, procedural aiming and animated muzzle positions. All eleven recovered assault rifles select their source animation family: default (`3`), QBZ, QBZ2 or shotgun-style. The source `SoldierAnimationController` maps these by weapon type; the manifest's rifle binding chooses the family, never a packet. `MoveCover` follows a validated recovered NavMesh path at the trusted manifest speed, after the existing one-tick destination delay. While moving, the server samples the corresponding `run`, `qbz_run`, `qbz2_run` or `shotgunner_run` clip at each 30 Hz tick, places hitboxes at its authoritative interpolated position and sends the pose to Unity. A move retains an already scheduled cover shot; a later click while walking starts a fresh delayed shot. Clicked movement and reload reset the stopped-shooting flag without erasing a pending target. Walking fire now uses the recovered delayed-first-shot path, server ammo/cadence checks, a source `shootAdditive` upper-body mask, and an explicit protobuf snapshot field. Full movement transition blending and normal-controller input ownership remain open.

The first accepted click can return `shot-scheduled` without consuming ammo. The host advances uncover animation and emits the shot after the recovered delay, rechecking weapon eligibility before consuming ammo. Consecutive 30 Hz ticks advance poses and projectiles; repeated observations do not advance animation twice. Critical rolls originate on the server. Map occlusion remains authoritative, and snapshots report health changes. Results always retain `RewardEligible=false`.

Signed manifests may now carry up to eight canonically ordered equipped slots. In rifle mode each admitted slot must match its recovered inventory index and exact source upgrade stage. The Worker retains clip, reserve, reload deadline and cadence deadline independently for every slot. `SwitchWeapon(slot)` is reliable and idempotent, rejects unallocated slots and cover-motion changes, cancels a pending first shot, and changes the source animation/muzzle/stat family before later fire. A projectile retains the weapon source that created it, so switching before impact cannot alter shield attribution. The compact snapshot publishes the active slot plus the active slot's existing ammo/timing fields; inactive state stays authoritative in the Worker and is returned when that slot becomes active.

Two additional player snapshot counters report confirmed opposing-player projectile hits and kills. A `Fire` command, aim ray, client claim or trusted direct-damage helper cannot increment them; one finished flight reaching a player and applying damage can. Lethal damage credits one kill to the actual shooter before the terminal snapshot is published. They are combat evidence only, not a durable reward or the complete recovered `StatsManager.MatchStats` record. The Client separately tracks shots, kills, vehicles, units, crates, cards, ribbons and match outcome, which still need complete mode integration.

Validation on Windows: the City map encounter passes in-process and through two independent `War.Client.MatchConnection` instances against the actual `NetworkWorker`. Tests verify delayed first-shot ammo use, command replay, health loss, all eleven rifle family selections, route admission, pending-shot survival through a cover move, moving hitbox reconstruction and run-pose snapshots. The chosen Aztec firing lane is blocked by exported geometry; it was not removed to make damage tests pass. These tests do not establish every map's runtime initialization or full PhysX parity.

Snapshots now carry optional `BattlePlayerState.rifle_pose` (tag 22): the actual sampled tick, one to four weighted source clip layers, root rotation, body-local rotation and optional upper-local override. Clip IDs are fixed protocol identities, not weapon enum values. The double-valued clip clock preserves selection of the same held 30 Hz samples. A command can change the next animation instruction while its response still reports the last sampled pose; no pose is published before the collision simulation uses it. Snapshot cloning and receipt replay preserve that distinction.

Tests reconstruct both player hitboxes and the rifle muzzle from protobuf-round-tripped pose data at every encounter tick. A conservative maximum-width two-player/four-layer packet including both walking-shot overlays remains within the authenticated 1,200-byte datagram limit. Both real UDP SDK clients receive pose snapshots, and the regenerated portable SDK is installed in the Unity project. The normal recovered DeathMatch path now installs the production bridge that renders this data after authoritative Running admission.
