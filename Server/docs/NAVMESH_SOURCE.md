# Recovered multiplayer NavMesh sources

Each of the five multiplayer scenes has one `NavMeshSettings.m_NavMeshData` reference. The exact Unity 2018.3.0f2 binary assets are copied to `Server/content/navmesh/` and pinned by `recovered-army-navmesh-sources.json` in the combat package. `extract_army_navmesh_sources.py --check` compares both the mapping and binary copies with the recovered Client. Startup rechecks every binary digest before accepting a source-bound match.

A disposable Unity 2018.3.0f2 project under `Server/.local/navmesh-export` loaded each copied `NavMeshData` with `NavMesh.AddNavMeshData` and exported `NavMesh.CalculateTriangulation` through `Server/tools/UnityNavMeshExport.cs`. The five outputs contain **21,038 vertices and 9,658 triangles** in total. `package_navmesh_triangulation.py` copies the outputs into `Server/content/navmesh-triangulation/`, pins their byte digests in `recovered-navmesh-triangulation.json`, and checks that package against the Unity export. Worker startup validates every triangle index, coordinate, area and source binding. The disposable Unity project is not a Client dependency.

`NavigationAgent` delegates ground routes to Unity `NavMeshAgent`; `EnemyController.WalkingUpdate` changes state only when `EnemyPoint.IsEnemyPointReached` reports planar distance below 0.04, then `SwitchState` uses the point's source state. `SwitchStateToRusher` stops the agent, interpolates position over 0.5 seconds and rotation over 0.3 seconds, and sets the next shoot time to 0.5 seconds later. The host now publishes source-corner-backed Rusher motion for exact complete spawn/point pairs; collision and firing remain separate.

`MatchEngine.RusherWalkingRoute` now binds a spawned host entity to its occupied Rusher slot on the pinned map and requests a covered route from the entity's current position. Four simultaneously spawned Rusher entities pass this match-owned binding test; death removes the route with the source slot. The method itself only projects a route; the match-owned motion state advances covered routes and applies the 0.04 arrival gate. It does not enter a firing state.

At spawn, the match creates an `ArmyRusherArrivalState` for each planar-covered Rusher route using the server-authored effective infantry speed. It advances once per active simulation tick, stops with reconnect pause, invalidates if the opponent leaves the reserved cover, and is removed on confirmed death. The four-Rusher match test checks that these four host positions move from their source spawn points and publish position ticks without advancing the roster revision. Once its strict first-shot delay has elapsed, the match can project the currently bound Moving target as an initial shot candidate. This does not grant the motion state collision, firing, damage, or visual authority.

The protobuf army-entity projection now carries a per-entity `position_tick` and a batch `server_tick`. The existing paged `revision` continues to represent roster/health changes, so the 30 Hz position updates can carry timestamps without forcing every reconnect page to restart. Spawned entities begin with `position_tick=spawn_tick`; covered Rushers then publish their host motion position and current simulation tick. The SDK rejects a position sample before spawn or after the batch tick. Multi-agent avoidance and corner-steering fidelity still require comparison before these positions can become collision or combat authority.

`LiveRusherUdpTests` starts a signed two-peer Worker match, deploys a recovered Rusher option, and polls entity pages from both SDK connections. It checks moved positions, bounded position ticks, matching entity keys, and unchanged roster revision across movement. This exercises actual UDP framing and pagination; it does not exercise the original Unity battle controller or model rendering.

The recovered `EnemyPoint.IsEnemyPointReached` checks strict planar distance `< 0.04`; `EnemyController.WalkingUpdate` invokes `TargetReached` only while walking, with a non-null point and no pending shot. A Rusher point selects `EnemyAIState.Rusher`. `SwitchStateToRusher` stops the agent, starts a 0.5-second `TweenPosition` to the point's XZ location while retaining the current Y, and sets the next shot time 0.5 seconds later. The source `enemy.prefab` serializes tween method 3 (EaseInOut) with `steeperCurves=0`, matching NGUI `UITweener`'s `t - sin(2πt)/(2π)` curve. The separate `ArmyRusherArrivalState` candidate now advances the strict gate, 15-tick settle, and greater-than-15-tick first-shot delay on all eight motion routes. It publishes covered Rusher positions and now restarts after a validated retarget, but grants no attack or firing authority.

The pinned `recovered-army-deployment.json` distinguishes MainScene's serialized `baseSpeed` from the runtime `ArmyUpgrades.MOVEMENTSPEED` for all 24 behavior families. `UpgradeSlotsGeneric.LoadData` replaces the base value with `MOVEMENTSPEED` before applying `Perk.speedCoef`; `EnemyController.UpgradesLoaded` then assigns that effective result to `NavigationAgent`. For example, serialized Swat speed 0.9 becomes sheet speed 1.0, and serialized helicopter speed 0.8 becomes sheet speed 3.0 before perks. The catalog validates the sheet binding and computes a bounded effective speed from a trusted coefficient. A signed match manifest can carry one `ArmySpeedCoefficients` value per equipped unit; a spawned entity retains the result in a private host ledger, removed on death. A client command cannot supply the coefficient. Live unit motion still requires a source-matched NavMeshAgent movement model; a trusted speed alone is not sufficient.

In the recovered C# source, `Perk.speedCoef` defaults to 1 and the only explicit assignment that changes it is `UpgradeSlotsAssaultHelicopter`; no ground-infantry speed override was found. The 0.8, 0.9, and 1.0 Unity probes therefore cover every recovered stock ground-infantry movement speed. The generic trusted coefficient remains a compatibility input, but a non-default ground-infantry coefficient is not established by this source audit.

The same artifact pins the common infantry `GameObject/enemy.prefab` NavMeshAgent digest and settings: radius 0.17, acceleration 10, angular speed 600, height 0.52, stopping distance 0, auto braking/repath enabled, and obstacle avoidance type 1. The prefab's initial speed is 0.8, but `EnemyController.UpgradesLoaded` replaces that with the effective behavior speed. These serialized settings are validated at startup; they are not yet a reproduction of Unity's avoidance or acceleration trajectory.

`UnityNavMeshMotionExport.cs` runs pinned spawn-to-Rusher cases on all five maps in Unity 2018.3 Play Mode with their baked NavMeshes, common infantry agent settings, and source ground-infantry runtime speeds 0.8, 0.9, and 1.0. A second City case (`3296-3089`) exercises a route where the host planner previously had its largest measured length difference. `package_navmesh_motion.py` pins 2,863 ordered frame samples across eight cases, source asset/route/prefab digests, and arrivals in `recovered-navmesh-motion.json` and `navmesh-motion/`. Every Unity final planar gap is below the Client's 0.04 arrival gate. Editor startup introduces an initial pause; these are observed trajectories rather than a deterministic motion oracle. Additional routes, moving-agent encounters, and source state transitions remain required before using the published positions as combat collision authority.

`ArmyNavMeshMotionState` drives published 30 Hz Rusher positions over a planar-covered route. It uses trusted effective speed and pinned agent acceleration, with an inferred braking deceleration of 1.5 units/s². After aligning each Play Mode trace at its first moving frame, median / p95 / maximum planar position errors in Unity units are Aztec **0.044 / 0.134 / 0.137**, City `2950-2826` **0.100 / 0.227 / 0.228**, City `3296-3089` **0.224 / 0.244 / 0.247**, Desert **0.201 / 0.218 / 0.220**, Park at speed 1.0 **0.090 / 0.244 / 0.245**, Park at speed 0.8 **0.065 / 0.177 / 0.178**, Park at speed 0.9 **0.072 / 0.218 / 0.219**, and Snow **0.010 / 0.026 / 0.034**. The candidate reaches the 0.04 planar gate in all eight cases. These single-agent trajectories span all three recovered ground-infantry stock speeds, but do not establish Unity-equivalent avoidance, perk-adjusted speeds, moving targets, or source state transitions. The host uses this motion for covered Rusher positions and its strict arrival/settle gate, but not for hit or shot authority.

The City `3296-3089` Unity path has six corners and a 14.98-unit planar polyline. A full-component geometry audit confirms that it is planar-covered by the recovered mesh with only 0.033 units of sampled maximum vertical deviation. The original centroid corridor had eleven corners and a 16.61-unit smoothed path. Corridor-only and full-component shortcuts could not change its intermediate geometry; stronger direct-line penalties and reverse centroid search were also ineffective. A bounded visibility search over source NavMesh vertices near the direct endpoint segment now finds a 14.98-unit covered path without using the Unity path fixture as a routing input. The general planner remains useful for nonexact and later positions; exact complete spawn-to-Rusher pairs now prefer the verified Unity corners. Each candidate edge must be planar-covered by the connected walkable component and stay within 0.25 units of sampled surface height. The selected path is revalidated and replaces the corridor's published route points and length. The eight motion fixtures and all 416 complete path fixtures check this candidate. The visibility search is still a bounded approximation; further routes, moving agents, radius clearance, and avoidance remain to validate.

`build_navmesh_path_cases.py` creates the complete 432-case cross-product of each normal infantry spawn and every Rusher slot on opposing covers. A second disposable Unity export runs `NavMesh.SamplePosition` with a three-unit radius and `NavMesh.CalculatePath` for each case. `package_navmesh_paths.py` pins the cases, sampled endpoints, status and ordered corners in `recovered-navmesh-path-manifest.json` and `navmesh-path-results/`; Worker startup validates these against the source spawn/Rusher identities and the exact binary and triangulation revisions. Unity returned **416 complete paths and 16 partial paths**. All partial paths start from Snow's source spawn component 3042; they must remain partial until a route policy is established from Client behavior.

The Server welds coincident Unity-exported vertices at four decimal places, builds triangle connectivity, and locates sampled endpoints on the walkable surfaces. It validates that connectivity against all 432 Unity statuses at startup: 416 connected and 16 disconnected. A point outside the mesh fails closed. Two A* triangle searches generate portal corridors: ordinary centroid cost and a cost that favors triangles near the direct endpoint segment. Each smoothed segment is clipped analytically against its source triangle corridor; the bounded visibility candidate instead checks every segment against the entire connected walkable component. Only planar-covered candidates can be selected, and a connected pair with no covered candidate fails closed. All **416** complete Unity fixtures pass this XZ-plane coverage check. The shorter covered candidate fixes a repeatable wrong-side detour from Snow spawn component 2798. Across the 416 complete Unity fixtures, candidate lengths are median **1.00×** Unity, p95 **1.07×**, and worst **1.08×**. Tests bound those measured differences and report the largest cases. A separate 0.25-unit-spaced audit of the candidate segments against the selected walkable component finds at most **0.217** Unity units of vertical deviation across the fixture set; a 0.25 bound guards regression. This sampled measurement does not prove continuous surface contact or source-agent radius clearance. The generic planner is retained for positions that do not match a pinned spawn/point pair; it is not the preferred live route for an exact pair. Further route, corner-steering, radius-clearance, and avoidance comparisons are still needed before host positions can determine combat collision. Partial Unity paths are never promoted to complete. Movement and the arrival/settle projection are active; firing and damage authority are not.

`UnityNavMeshCrowdExport.cs` runs two source-speed 0.9 agents simultaneously on Park, from spawn 3251 to Rusher point 3551 and spawn 3443 to point 3429. `package_navmesh_crowd.py` pins 479 shared Play Mode frames per agent, their source endpoints and binary digests, and a minimum Unity planar separation of 0.394 units. At the aligned frames, independently smoothed generic host routes reached both points but diverged by up to 2.371 units; using the pinned complete Unity corner routes reduced maximum individual error to 0.250 units and yielded 0.415 minimum host separation. The Worker now selects those validated corners for any exact complete source spawn/point pair and falls back to its generic planner after position changes or where the observed polyline is not covered. This one two-agent trace is evidence for that selection, not proof of general Unity-equivalent avoidance.

A second disposable Park probe starts two speed-0.9 Rushers at source spawn 3443, nine frames apart, toward source points 3567 and 3177. `package_navmesh_staggered.py` pins their ordered Play Mode samples and digests in `recovered-navmesh-staggered.json`. Unity initially places the second agent within the two 0.17-radius footprints (0.183 planar units apart) and recovers to more than 0.34 units within four further frames. The host now evaluates each Rusher motion tick in stable entity-key order and rolls back a proposed step that would close an allied active Rusher below the combined 0.34 radius. An already-overlapping new spawn may move only if its step increases separation, allowing the older unit to clear the spawn. The four-unit match regression checks at least 0.34 separation once both members of a pair have been active for four ticks. This allied radius gate models source clearance; it is not a full reproduction of Unity NavMeshAgent obstacle avoidance for crossing routes or other unit families.

`park-crossing-result.json` pins a separate opposing-player encounter on Park: spawn 3251 to Rusher 3551 crosses spawn 3547 to Rusher 3497. The Unity agents both arrive, with a minimum planar separation of 0.392 units. The projection checks each short step against NavMesh endpoint connectivity, but this one fixture does not prove general Unity-equivalent avoidance, continuous radius clearance, or combat collision authority. Rusher firing and damage remain pending.

Retargeting needs a separate source comparison. `EnemyPointRusher.isActive` is true only while its `playerPoint.shield.player` exists. `EnemyController.RusherUpdate` accumulates inactive time only while no shot is pending, then uses a strict `> 1.5f` test before `FindBestRusherPoint`, `SetFinalTarget`, and `SwitchState(Walk)`; a brief active interval does not reset that accumulator. `FindBestRusherPoint` iterates `MiscTools.permutationsOfFOur` in its generated order across all four slots at the old and closest occupied enemy cover, requires the candidate to be free with its near neighbour (a distinct Rusher point within 0.2 units), favors destination indexes 0–1 by subtracting 1.7 from their distance score, and uses a strict lower-score comparison. A fixed-tick retarget clock pins the strict delay and its pause-without-reset behavior. A separate selector now reproduces the ordered four-slot permutation scan, strict score comparison, 1.7 index preference and index-zero fallback against supplied scene-neighbour occupancy predicates; its focused tests pin a uniquely eligible destination, a strict-score tie, and the fallback. The selector labels that fallback unqualified so it cannot be mistaken for an occupancy proof. The Worker now retains the old reservation and motion while the defending player leaves the cover. After the strict inactive timer, it runs the source permutation scan with the recovered near-neighbour predicate, verifies a free destination and a planar-covered route from the published host position, then transfers the slot and starts a new arrival state in one match tick. An unqualified source fallback or unavailable route leaves the old reservation intact and the timer ready for retry. The Rusher artifact now pins every PlayerPoint world position and its four slot positions. Worker startup reconstructs the source ordered three-unit PlayerPoint and 0.2-unit Rusher near-neighbour search: 24 directed links per map, with an occupied near point allowed when it is the moving unit old slot. The fixed-seed live match test proves old-slot release, new-slot ownership, route restart, and the later first-shot gate with three active Rushers. It then removes the other two host units to prove a second transfer of the same Rusher back to another source cover without leaking its intermediate slot. Arrival with all three Rushers active proved intermittent across earlier randomized spawn runs. The match now accepts an injected army-choice function for deterministic test setups while production keeps its existing random source; the retarget regression pins seed 2, which previously remained in Walking after 664 rejected ticks behind an ally. A bounded two-leg NavMesh detour around an allied radius now lets that layout reach the new point; the test requires a detour to have been used and checks at least 0.339 planar separation from its allies throughout the retarget. Focused seed sweeps 0–20 pass, but this candidate still lacks a matching Unity crowd trajectory. The fixed-seed arrival proof must not be read as source-equivalent allied crowd avoidance. Other cover-change permutations, shot scheduling, and damage remain unproven.

The Unity 2018.3 Park retarget crowd probe pins the seed-2 stalled host snapshot with one moving and two stopped NavMeshAgents (`recovered-navmesh-retarget-crowd.json`, 112 frames each).
