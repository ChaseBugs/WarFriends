# Bounded battle event cursor

The opt-in rifle and shotgun modes publish host-owned `Shot`, `Impact`, `PlayerDeath` and `Terminal` events, plus source-bound shield, barrel, army spawn/death, and DeathMatch overtime transitions when their authority is enabled. Accepted projectiles create a shot event after ammo authorization. A completed flight creates an impact event at its resolved collision point. Applied lethal damage creates one death event before the terminal event. The event IDs are monotonic within one match and are separate from command IDs, packet sequences and snapshot revisions. Client packets cannot submit an event or damage claim.

`MatchEventPoll.after_event_id` is the last event the participant has processed, not the last event it has received. The host returns at most four ordered events in a separate authenticated `MatchEventBatch`, keeping the maximum-width pose snapshot within the 1,200-byte datagram limit. Repeating a cursor replays its page. The two participants acknowledge independently; history is removed only after both have advanced past it. A reconnect uses the same match-owned cursor. An expired or future cursor returns an explicit error. `War.Client.MatchConnection.PollEventsAsync` and Unity's `SelfHostedBattleClient.FetchEvents` expose the raw contract without silently advancing a cursor.

Unity callers may subscribe to `SelfHostedBattleClient.CombatEventReceived`. In Play Mode, its `Update` polling loop invokes `DispatchEvents` on the Unity thread and advances `ProcessedEventId` after each successful callback. A callback failure leaves that event unacknowledged and it is fetched again. The owner can pass its persisted processed cursor to `Connect(grant, processedEventId)` after a signed reconnect. Callback side effects should be idempotent because an exception after a side effect can lead to a replay. Without a subscriber the adapter does not consume events. The Editor batch audit calls `DispatchEvents` explicitly; it does not verify the automatic `MonoBehaviour.Update` path in Play Mode or Android.

The event log is in memory and bounded to 512 entries per match. New projectile shots receive `event-backpressure` before ammo is consumed when existing flights and the terminal marker would exhaust that capacity. This prevents a silent gap during the current process, but it is not crash-durable event delivery. The existing UI does not yet consume these events, and reconnect requires the caller to retain its processed cursor. Full spawned-entity effects, damage/impact presentation identity, loss and reordering stress tests, persistent host recovery, and a durable Backend result handoff remain open under [B28/B30/B32](BATTLE_SERVER_FEATURES.md).

`War.Client.MatchOutcomeProjection` maps a validated terminal snapshot to each participant's recovered `GameController.GameEndReason` byte: `Win`/`Killed` for a lethal player death and `WinByForfeit`/`Forfeit` for a forfeit or reconnect loss. Running overtime and aborted matches project `None`. This gives the Unity integration an exact presentation contract without allowing the Client to decide the winner; it is not yet wired into the original battle UI.

Battle tests exercise exact replay, both-player acknowledgement, cursor expiry, page ordering, shot/impact/death/terminal ordering, real two-client UDP polling, signed-generation reconnect with a retained cursor, and maximum-width event packet size. A capacity stress test confirms that backpressure consumes no ammo, retains every event, and clears after both players acknowledge. The disposable Unity two-rig audit injects a presentation callback failure and verifies that the first event is replayed before its cursor advances. These checks establish the current event transport; they do not prove a complete original game presentation flow.
