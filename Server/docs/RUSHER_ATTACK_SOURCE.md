# Rusher attack contract (recovered 1.4.0 Client)

Source: `Clients/ExportedProject/Assets/Scripts/Assembly-CSharp/EnemyController.cs`, `SoldierBehaviourRusher.cs`, `SoldierBehaviour.cs`, `SoldierBehaviourDefinititon.cs`, `SoldierAnimationController.cs`, and the referenced legacy animation clips. This is the B14 Rusher attack contract and records the current verified host boundary.

1. `SwitchStateToRusher` stops the agent, begins a 0.5-second point-position tween, and sets `mNextShootTime = mTime + 0.5f`. `RusherUpdate` uses the strict `mTime > mNextShootTime` comparison. The host's `ArmyRusherArrivalState.InitialShotDelayElapsed` already models that first strict boundary; arrival alone never authorizes a shot.
2. An attempt requires `!mWillShoot` and a non-null player at the Rusher point's shield. `PrepareToShoot(true, false, 0f)` also requires `mCanShoot`. It calls `SoldierBehaviourRusher.PickRusherTarget`, which selects the nearest `Moving` target from that player; there is no line-of-sight or maximum-distance gate in this call. The host's `RusherInitialShotTarget` projects the first eligible target, but does not yet model `mWillShoot`, `mCanShoot`, or a shot.
3. `SoldierBehaviour.StartShooting` requires a target, rolls an integer fire batch in `[fireBatchSizeMin, fireBatchSizeMax)` and clamps it to 0–14, selects the shot type, and rolls one real/fake bit per batch shot using `probabilityOfRealShot`. The effective definition is interpolated and perk-scaled; its precise value must come from trusted army catalog/loadout authority. A zero batch is possible from malformed/unusual source values and must not become a free hit.
4. For ordinary Rusher rifle-family weapons, `PrepareToShoot` starts `ShootStand` and delays `Shoot` by 30% of the weapon's standing-shot animation length; flamethrower uses zero delay. SWAT weapons use the shield-uncover length. `Shoot` schedules `ShootJustStarted`, then `ShootingFromWeapon` invokes `SoldierBehaviour.Shooting` while the shooting state and life remain valid. The latter checks `currentWeapon.willShoot`; a secondary weapon fires once and switches back after 0.5 seconds. Other batches choose real or deliberately offset fake rounds, call `OnShot`, and end after the batch count.
5. `EndShooting` clears both shooting flags. `ReturnToPreviousStateFromShot` replaces the Rusher cooldown with `mTime + Random.Range(2f, 4f)`, overriding the generic `minShootTime/maxShootTime` roll. Retarget timing pauses while a shot is pending. Death, cover departure, target loss, retarget, and match end must cancel or invalidate pending host shot work before it can deal damage.

The army deployment artifact pins the five serialized base shot fields for all six scene-backed `SoldierBehaviourRusher<T>` families, and the runtime catalog composes normal, special, and elite source rows before applying trusted perk accuracy. The version-three Rusher weapon artifact additionally pins each first weapon's recovered type and its exact windup rule: zero ticks for Flamethrower, nine ticks for ordinary one-second stand-shoot clips, and 30 ticks for SWAT's one-second `shield_unhide`. Each clip path, byte digest, and serialized legacy length is part of the combat revision. `ArmyRusherAttackState` owns eligible -> windup -> ordered batch -> cooldown, including real/fake rolls, weapon cadence, and the source 30 Hz timing domain. After a batch, it uses the Rusher-specific 2-4 second cooldown from `ReturnToPreviousStateFromShot` rather than the generic upgrade-row shoot time.

Match-owned Rusher state creates bounded shot intents only after moving-target and post-arrival gates pass. At `PrepareToShoot`, it copies the current Moving target position into a match-owned batch latch, reuses that exact position for every shot in the batch, and pauses the 1.5-second inactive-cover retarget clock while the attack is in windup or firing. Batch completion clears the latch, a committed retarget replaces it only after no shot is pending, and entity death removes it. Projectile-backed families advance entity-owned flight against current recovered player poses, validate impacts, apply player health through the shared damage kernel, and publish shot/impact events. Flamethrower owns its separate six-pulse overlap path. No client packet chooses real/fake bits, target, damage, windup, or cooldown.

Remaining work includes a Unity timing comparison, runtime weapon/economy identity resolution, shield/barrel and other spawned-entity impacts, unsupported Commando behavior, complete replay projection, and normal Client effects.

The serialized reference extractor pins six EnemyBasicInventory weapon-reference rows in `recovered-rusher-weapon-bindings.json`, including the SWAT two-weapon inventory. It records source GUID/file IDs and resolves them to recovered prefab paths and serialized weapon types (Shotgun=7, assault rifle=0, SWAT pistol=3, flamethrower=12). Runtime dictionary IDs and economy rows remain unresolved and must be bound before shield/barrel coefficients are enabled.
