# Rusher attack contract (recovered 1.4.0 Client)

Source: `Clients/ExportedProject/Assets/Scripts/Assembly-CSharp/EnemyController.cs`, `SoldierBehaviourRusher.cs`, `SoldierBehaviour.cs`, and `SoldierBehaviourDefinititon.cs`. This is a contract for B14, not a claim that host firing exists.

1. `SwitchStateToRusher` stops the agent, begins a 0.5-second point-position tween, and sets `mNextShootTime = mTime + 0.5f`. `RusherUpdate` uses the strict `mTime > mNextShootTime` comparison. The host's `ArmyRusherArrivalState.InitialShotDelayElapsed` already models that first strict boundary; arrival alone never authorizes a shot.
2. An attempt requires `!mWillShoot` and a non-null player at the Rusher point's shield. `PrepareToShoot(true, false, 0f)` also requires `mCanShoot`. It calls `SoldierBehaviourRusher.PickRusherTarget`, which selects the nearest `Moving` target from that player; there is no line-of-sight or maximum-distance gate in this call. The host's `RusherInitialShotTarget` projects the first eligible target, but does not yet model `mWillShoot`, `mCanShoot`, or a shot.
3. `SoldierBehaviour.StartShooting` requires a target, rolls an integer fire batch in `[fireBatchSizeMin, fireBatchSizeMax)` and clamps it to 0–14, selects the shot type, and rolls one real/fake bit per batch shot using `probabilityOfRealShot`. The effective definition is interpolated and perk-scaled; its precise value must come from trusted army catalog/loadout authority. A zero batch is possible from malformed/unusual source values and must not become a free hit.
4. For ordinary Rusher rifle-family weapons, `PrepareToShoot` starts `ShootStand` and delays `Shoot` by 30% of the weapon's standing-shot animation length; flamethrower uses zero delay. SWAT weapons use the shield-uncover length. `Shoot` schedules `ShootJustStarted`, then `ShootingFromWeapon` invokes `SoldierBehaviour.Shooting` while the shooting state and life remain valid. The latter checks `currentWeapon.willShoot`; a secondary weapon fires once and switches back after 0.5 seconds. Other batches choose real or deliberately offset fake rounds, call `OnShot`, and end after the batch count.
5. `EndShooting` clears both shooting flags. `ReturnToPreviousStateFromShot` replaces the Rusher cooldown with `mTime + Random.Range(2f, 4f)`, overriding the generic `minShootTime/maxShootTime` roll. Retarget timing pauses while a shot is pending. Death, cover departure, target loss, retarget, and match end must cancel or invalidate pending host shot work before it can deal damage.

The army deployment artifact now pins the five serialized base shot fields for all six scene-backed `SoldierBehaviourRusher<T>` families and the runtime catalog validates their identity, shape, and value bounds before use. `ArmyRusherAttackState` now models the server-owned eligible → windup → ordered batch → cooldown state, including real/fake rolls and the source 30 Hz timing domain. Match-owned Rusher state now creates bounded shot intents only after the moving-target and post-arrival gates pass; intents carry the target transform, batch position, and server-selected real/fake bit but do not apply damage. `ArmyRusherImpactResolver` now validates a collision against that intent and trusted damage into an army-specific impact proof without mutating player health. Match consumption rejects fake intents before damage. `ArmyProjectileFlight` now advances an entity-owned projectile at contiguous 30 Hz ticks and returns a validated entity-keyed impact, without using player ownership rules. These are base definitions only; `LoadData` upgrades and perk scaling can change effective values. The strict source digest/extractor check is required in addition to runtime bounds.

Implementation remains open: bind each Rusher weapon and **effective** definition to validated source/catalog rows; add a match-owned pending shot/batch state with server-owned randomness and strict tick deadlines; feed the army projectile impact proof through the live player hitbox, shield, barrel, and armor paths; the entity-owned flight and player-health adapter are now present, and the Worker tick loop now launches and advances these flights against current recovered player poses. Shield/barrel-specific army impact effects and full replay coverage remain open; publish shot and impact events with reconnect/replay; compare animation timing and hit outcomes against Unity; and test multiple Rushers, moving defenders, retarget during windup, death, and terminal freeze. No client packet may choose real/fake bits, target, damage, or cooldown.


The serialized reference extractor now pins six EnemyBasicInventory weapon-reference rows in `recovered-rusher-weapon-bindings.json`, including the Swat two-weapon inventory. It deliberately records source GUID/file IDs and resolves them to recovered prefab paths and serialized weapon types (Shotgun=7, assault rifle=0, Swat pistol=3, flamethrower=12). Runtime dictionary IDs and economy rows are still unresolved; a later catalog step must bind those identities before shield/barrel coefficients are enabled.
