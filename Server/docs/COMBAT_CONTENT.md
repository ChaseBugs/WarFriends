# Pinned combat content at Worker startup

Set `Battle__CombatContentManifestPath` to the absolute path of `Server/content/combat-content-manifest.json` to validate source-bound allocations. The package uses fixed neighboring filenames for recovered battle sheets, the [complete weapon binding graph](WEAPON_BINDINGS.md), rifle bindings, player poses and shot targets, barrel scene bindings, Unity barrel overlap audit, army deployment and spawn points, Rusher-slot bindings, scene-bound NavMesh binaries in `navmesh/`, Unity-exported geometry in `navmesh-triangulation/`, and source route cases/results in `navmesh-path-results/`, so the same directory layout works on Windows and Linux. No Unity process or database is needed to load it.

The version-one manifest pins the MainScene digest and SHA-256 revisions of the stats, bindings, poses, barrel bindings/overlap, army deployment, army spawn-point, army Rusher-point, player shot-target, NavMesh-source, Unity triangulation, and Unity path-fixture artifacts. Startup validates each catalog, including all 29 barrel source bindings, 58 Unity overlap probes, 101 army spawn components, 160 Rusher slots, both five-target serialized player lists, five distinct scene-bound NavMesh binary digests, 9,658 triangulated walkable polygons, and 432 source-bound Unity paths, before accepting a match. A server triangle-connectivity graph must agree with all 416 complete and 16 partial Unity path statuses; this does not yet calculate route corners. `BattleCombatContent.Revision` hashes `WarFriends/combat-content/v1\n` followed by all manifest digests in declared order, joined with `\n` and no final newline. Artifact changes require an explicit pin update after export validation; silently accepting new content is not supported. The Rusher Moving target follows the sampled rig; other shot-target reference positions alone do not establish animated world positions or AI firing authority. See [NavMesh source boundary](NAVMESH_SOURCE.md) for the remaining route work.

Every match on a configured Worker must use that composite revision as `CatalogRevision`. Both participants must supply `WeaponUpgrade`, the recovered zero-based upgrade-row index. The weapon assertion must exactly equal `content.Stats.CreateManifest(sourceId, upgrade)`, including binary32 source values represented in the double-valued manifest fields. Generate these values through the catalog instead of rounding them by hand. Unknown rifles, incomplete allocations, wrong revisions, invalid indexes and altered ammo/cadence/reload values fail before admission.

For source scene barrels, the optional signed `SceneMasterPlayerId` must name one of the two participants and both must supply zero-based `PlayerLevel` values from the 43 recovered `Google2u.Levels` rows. `PhotonView.isMine` makes a zero-owner scene barrel belong to the master client; the dedicated host uses that selected participant's level for the barrel health formula. These fields come from the allocator, never player commands. Barrel instances are initialized internally, but projectile damage, explosions and barrel state on the wire remain closed.

Without the package, existing synthetic unscored manifests remain available for diagnostics. A manifest containing `WeaponUpgrade` cannot silently fall back to that path. Omitted upgrade fields are excluded from manifest hashing, preserving existing synthetic manifest digests. This is server deployment input, not a client-provided entitlement: the future Backend allocator still must prove ownership and upgrades.

Content validation runs through NetworkWorker -> MatchRouter -> MatchEndpoint -> MatchEngine. The opt-in [rifle mode](LIVE_RIFLE_COMBAT.md) also installs live projectile simulation and uses map geometry from this pinned package. Rewards and normal Unity battle-controller integration remain unavailable.

For the separate `unscored-shotgun-combat` mode, also set `Battle__ShotgunContentManifestPath` to the absolute `Server/content/shotgun-content-manifest.json`. It pins nine scene shotgun bindings and 464 upgrade stages to the same MainScene. The Worker binds their muzzle nodes into the validated rig at startup. This mode uses `BattleCombatContent.ShotgunRevision`: SHA-256 of UTF-8 `WarFriends/shotgun-combat/v1\n`, the rifle combat package revision, `\n`, and SHA-256 of the shotgun manifest bytes. Use that value as the match `CatalogRevision`, and obtain each `WeaponManifest` from `ShotgunCatalog.CreateManifest` for the owned zero-based stage. A rifle revision or Client-asserted ammo/reload/rate is rejected before admission. See [shotgun source](SHOTGUN_SOURCE.md) for live player-and-shield boundaries.

For `unscored-smg-combat`, set `Battle__SmgContentManifestPath` to `Server/content/smg-content-manifest.json`. The Worker validates all eight SMG identities and 398 stages, binds their muzzle nodes and recovered default/pistol/QBZ2 animation families, and requires `BattleCombatContent.SmgRevision` plus an exact `SmgCatalog.CreateManifest` result. The live host owns the three-round burst after the first command. See [SMG source](SMG_SOURCE.md). Mixed combat is enabled only when the shotgun, SMG and pistol packages are all loaded, as described below.

For `unscored-pistol-combat`, set `Battle__PistolContentManifestPath` to `Server/content/pistol-content-manifest.json`. It validates six identities and 306 stages plus the source `Pistol.ammoLeft == int.MaxValue` override. Mixed combat additionally requires the burst-LMG package described below and pins every loaded class catalog in `MixedRevision`; each slot resolves through its exact class package. See [pistol source](PISTOL_SOURCE.md).

For `unscored-lmg-combat`, set `Battle__LmgContentManifestPath` to `Server/content/lmg-content-manifest.json`. It validates the eight burst-LMG identities and 398 stages while excluding the separately controlled minigun. Set `Battle__MinigunContentManifestPath` to `Server/content/minigun-content-manifest.json` for `unscored-minigun-combat`, its 36-stage source package, held-input clock, family-4 poses and projectile authority. Mixed combat derives its revision only when shotgun, SMG, pistol, burst-LMG and minigun packages are all pinned. See [LMG source](LMG_SOURCE.md) and [minigun source](MINIGUN_SOURCE.md).

Validation: source-bound allocation succeeds; missing package, forged weapon values, wrong stage/revision and altered artifact pins reject. Actual Worker construction validates the package and rejects altered reserve ammunition. The current Windows battle suite passes 72,976 assertions; the solution builds with zero warnings/errors; the protocol suite passes 1,025 checks. The minigun slice contributes 19 package/timing/MatchEngine assertions and five real UDP checks. Native Mongo/HTTP/protobuf/UDP smoke remains a separate release gate.
