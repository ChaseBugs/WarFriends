# Fresh .NET server guidance

- The owner confirms Client recovery is complete; focus on reconstructing Server behavior from the active recovered Client. Follow its gameplay logic, data, exact communication contracts, callback order, and rollback semantics for every feature. Verify builders, parsers, and callers before implementation; keep server-owned outcomes authoritative and document missing server-only policy rather than inventing it. Do not reshape Client gameplay to accommodate the Server foundation.
- Follow the owner's accepted design: ASP.NET Core backend and separate .NET battle Worker, MongoDB persistence, protobuf, native Windows/Linux processes, no Docker or Photon dependencies.
- Keep this first networking/account checkpoint distinct from a complete game implementation. Do not label the connectivity endpoint as matchmaking or award rewards from probe packets.
- Inspect current 1.4.0 client builders/parsers before implementing legacy behavior; use the generated inventory as an index, not an exhaustive semantic specification. Preserve source evidence and version distinctions.
- Keep session signing secrets in server-only `War.Infrastructure`; distribute only the portable `War.Shared` and `War.Client` dependencies to Unity.
- Database writes belong in the backend. Future inventory/reward/settlement operations require validated server authority and atomic idempotency; multi-document Mongo transitions require a replica set.
- Bound datagrams, queues, sessions, replay windows, and reassembly before adding gameplay traffic. ACK metadata alone is not reliable delivery. Do not turn arbitrary original RPCs into authoritative server commands.
- Run `dotnet build WarFriendsServer.sln`, `dotnet run --project tests/War.Protocol.Tests`, and the native Mongo smoke for networking/account changes. On Windows use `scripts/Smoke.ps1`; on Linux use `scripts/smoke.sh`. Do not claim Linux or Unity runtime verification from cross-publishing alone.
- Changes to the legacy channel (`src/War.Backend/Legacy/`, `LegacyPlayerStore`, `LegacyBufferStore`) must also pass `scripts/LegacySmoke.ps1`, which asserts the exact wire shapes the shipped client parses. When adding an action, first read its request builder in `BeanstalkServerManager`, its `On<Action>` handler (or, for a buffered action, its case in `ServerResponseHandler.ProcessBuffer`), and note which response keys are indexed *without* a `ContainsKey`/`!= null` guard — those are mandatory; the rest are read only on specific failure codes and must carry authoritative rollback state there. Add assertions for them rather than assuming the shape.
- Buffered economy/catalog actions (`BuyWeapon`, `BuyUnit`, `BuyCardPack`, `ClaimAssignment`, …) need the Google2u price/reward sheets before they can be implemented for real. Until that catalog is imported, they must keep returning `ServerMaintenance` rather than a fabricated `Success` — a granted purchase the server cannot price is worse than a refused one. `LegacyBufferProcessor.Implemented` is the explicit allowlist; extend it only alongside the catalog data an action actually needs.
- Client and server run **offline with no Photon Cloud reachable**. Battle transport is the `War.BattleServer` UDP host. Never emit the `Regions` player field or otherwise imply a Photon region; never make the boot path depend on Fuse, Kochava, Google Play or AWS.
- Keep the owner's concurrent Client edits intact. Any Photon removal must preserve scene/prefab identities and be preceded by a verified replacement for each relevant behavior.
